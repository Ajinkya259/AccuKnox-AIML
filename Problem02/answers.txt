2. KEY COMPONENTS OF AN LLM CHATBOT

1.  UI: the place where users talk to the bot, could be a website, app, WhatsApp or even a call.
2.  LLM provider: the model that actually genrates replies, like OpenAI, Anthropic or Llama.
3.  System prompt: basic rules for the bot, how it should talk and what it shouldnt answer.
4.  Knowledge (RAG): pulls the relevent company docs and passes them to the model.
5.  Tools: so the bot can do things, like look up an order or raise a ticket.
6.  Context and memory: what the bot keeps from earlier chats and about the user.
7.  Guardrails: to stop wrong, unsafe or off-topic answers.
8.  Rate limits and cost: keeping API calls and spend under control.
9.  Tracing/observability: logs each step so when somthing breaks we can see why.
10. Evaluation: regular testing to make sure answers don't get worse over time.


3. VECTOR DATABASES

What is it?
A vector database stores text as numbers (vectors) so we can search by meaning
and not just by exact words.

Example: "I forgot my password" and "how do I reset my login?" are worded
diffrently but mean the same thing. In a vector DB both end up close to each
other, so searching one finds the other.

How it works
1. Break the documents into small chunks.
2. Run each chunk through an embedding model to get its vector.
3. Save the vectors with some extra info like date or category.
4. When a question comes in, turn it into a vector too.
5. Pick the vectors that are closest to it, those are the best matches.

Common options
- FAISS    : very fast, but its a library, not a full database
- Pinecone : managed cloud service, nothing to set up or host
- Qdrant   : open source, can run on our own servers, good filtering
- pgvector : adds vector search inside PostgreSQL
- Chroma   : simple and easy, good for small projects

My choice
Problem: a security team wants an assistant that finds old incidents similar to
a new alert. They should be able to filter by severity and date, and the data
has to stay on the company's own servers.

I would go with Qdrant because:
- It can be self hosted, so sensitive data never leaves the company.
- It filters while searching, like "similar incidents, only critical, last 90 days".
- It supports keyword search along with vector search, which matters for exact
  things like CVE numbers and IP adresses.
- It's fast and free when we host it ourselves.

From my own work: I used Pinecone in a voice support agent, and FAISS with keyword
search over 13.98 million Wikipedia passages, so I've seen why filtering and
keyword matching are needed alongside plain vector search.
